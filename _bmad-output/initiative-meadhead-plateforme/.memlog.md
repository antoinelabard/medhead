- (decision by user) 2026-11-16 Préparation à la production placée dans une initiative séparée sous une initiative parente ; la PoC reste inchangée et livrable telle quelle.
- (decision by user) 2026-11-16 Briques à construire réellement dans Docker (pas seulement documenter) : passerelle API, service IAM, base de données redondante, monitoring et journaux (Grafana, Graylog).
- (decision by user) 2026-11-16 Objectif : que les développements continuent après validation de la PoC, avec de nouvelles fonctionnalités, dans une architecture microservices cadrée côté DevOps.
- (requirement) R1 (exigences ; décision 2026-11-16) La PoC du système d'intervention d'urgence est livrée et validée selon initiative-meadhead-poc.
- (requirement) R2 (décision 2026-11-16 ; dda §Architecture cible) Un point d'entrée unique route le trafic web vers les services, termine TLS et limite le débit ; un service n'est joignable de l'extérieur que par lui.
- (requirement) R3 (décision 2026-11-16 ; principes C3) Un service IAM OIDC authentifie les utilisateurs et porte rôles et permissions ; un appel sans le rôle requis est refusé par le service.
- (requirement) R4 (décision 2026-11-16 ; principes B1) Les données ont des sauvegardes automatisées dont la restauration est testée, une redondance qui survit à la perte d'un nœud, et des réplicas en lecture seule qui servent les lectures sans charger le primaire.
- (requirement) R5 (décision 2026-11-16 ; principes B1, C3) Les métriques système et applicatives sont visibles dans Grafana et les journaux de tous les services sont centralisés et consultables dans Graylog.
- (requirement) R6 (décision 2026-11-16 ; exigences §Exigences bloc de construction ; dda §Objectifs) Un nouveau microservice s'ajoute en suivant un modèle documenté (pipeline, image, routage, IAM, supervision) sans modifier les services existants.
- (constraint) Stack et outillage communs : Java/Spring Boot, Angular, Docker, GitHub (issues, PR, Actions), Gitflow (décisions 2026-11-16).
- (constraint) Données factices ou anonymisées uniquement (principes C4-II ; dda §Limites).
- (constraint) La seconde initiative ne modifie pas le livrable PoC ni sa mesure de 200 ms par instance de service (décision 2026-11-16).
- (assumption) La seconde initiative démarre une fois la PoC validée, sur ses fondations (socle Docker et CI de l'epic 1, API de recommandation comme premier service).
- (question) Environnement cible du socle de production : Docker Compose sur un hôte, Docker Swarm ou Kubernetes ? Attend l'architecture.
- (question) Le socle de production est-il déployé par le pipeline vers un environnement réel, et lequel ? La mission l'interdit pour la PoC seulement.
- (question) Graylog sert-il seulement à la collecte des journaux ou aussi de SIEM (règles de détection, alertes de sécurité) ?
- (note) Piste à trancher par l'architecture : utiliser dès la PoC le même IAM (par exemple Keycloak avec un realm de test) comme fournisseur d'identité factice, pour éviter de le refaire.
- (decision by user) 2026-11-23 Initiative parente, découpage en deux initiatives et enveloppe de initiative-socle-production approuvés.
- (decision by user) 2026-11-23 R5 réutilise la supervision de performance livrée par la PoC (son R15) et l'étend à tous les services, avec Graylog pour les journaux.
